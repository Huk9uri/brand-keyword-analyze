## 3. 파일 의존성 제거 및 VIEW 조회 구조 개선

기존 `smartplace_crawler_V2.2_jadong.py`는 파일에 관리하던 매장 목록을 수집 대상으로 사용했습니다. 이 방식은 ERP의 매장 상태와 수집 목록이 별도로 관리되어, 신규 매장·폐점·계정 변경 사항을 일관되게 반영하기 어려운 구조였습니다.

수집 대상을 `naverDB.dbo.vw_naver_store_hours_targets`에서 조회하도록 변경하고, 별도 대상 로더에서 브랜드와 로그인 계정에 맞는 매장만 반환하도록 구성했습니다. 기존 파일은 초기 대조 자료로 보존하되, 운영 대상 조회 시 파일로 되돌아가는 대체 경로는 두지 않았습니다.

VIEW의 기존 ERP 대상 조건과 원래 16개 컬럼은 유지하고, 다음 3개 컬럼을 추가했습니다.

초기 반복 조사 관련 테스트 54개, 전체 매장 확장 과정의 테스트 실행 572개 통과를 확인했습니다. 후속 보고서 수정에 대해서는 관련 테스트 19개를 추가 확인했습니다. 서로 다른 실행 범위이므로 테스트 수를 합산하지 않았습니다. 기능 구현과 검증은 완료했으나, 전체 매장 확장 변경은 작업 트리에 남아 있어 커밋·PR 완료와 구분합니다.

기존 VIEW의 한촌 140곳과 ERP 운영 기준의 한촌 146곳은 조회 조건이 다른 모집단입니다. 스마트플레이스 관리 계정에 연결된 55곳, 공개 Place ID가 확보된 136곳, POS 분석 대상도 각각 다르므로 동일한 전체 매장 수로 혼용하지 않습니다.

## 9. 한촌 매장 좌표 확보 및 DB 적재

전체 매장 검색 순위 조사에 앞서 기존 좌표 수집 방식을 활용해 공개 플레이스 페이지에서 좌표를 추가 확보했습니다. 저장 테이블과 컬럼이 이미 존재하는지 확인한 뒤 기존 구조에 적재했습니다.

| 항목 | 확인·처리 결과 |
| --- | --- |
| 저장 테이블 | `naverDB.dbo.naver_place_location` |

공개 Place ID·좌표는 검색 순위 조사에 사용하고, 스마트플레이스 관리 ID·로그인 권한은 유입 통계 수집에 사용합니다. 스마트플레이스 관리 ID가 없는 매장도 공개 Place ID와 좌표가 확보되면 순위 조사 대상이 될 수 있습니다.

## 13. 차일 업무 계획

1. **정기 수집 운영 점검:** VIEW 기반 수집의 다음 예약 회차에서 계정별 대상 수·실패 여부·DB 갱신 상태를 확인합니다.
2. **통계 정합성 검증:** 적재된 매장별 날짜·키워드·유입수를 재조회하여 누락·중복을 점검합니다.
