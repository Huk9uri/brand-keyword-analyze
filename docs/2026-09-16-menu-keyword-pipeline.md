# 매장별 메뉴 기반 키워드 발굴 실행 안내

## 한 번에 실행하기

저장소 루트 `C:\workspace\brand_analyze`에서 실행한다. 출력 경로를 지정하지 않으면 `outputs/menu-keywords-한국시간실행시각-고유ID` 폴더를 자동 생성한다. 같은 명령을 반복해도 기존 결과를 덮어쓰지 않는다.

```powershell
.venv/Scripts/python.exe -m scripts.menu_keyword_pipeline.cli --collect --allow-write --allow-network
```

실행일은 한국 시간으로 계산하고 직전 30일을 조회한다. 2026-09-16 실행이면 2026-08-17 이상, 2026-09-16 미만이다. POS 원천은 한 번의 GROUPING SETS 집계로 메뉴별 수량·금액과 일별 관측을 읽으며 두 합계를 대조한다. 당일 매출과 미래 날짜는 포함하지 않는다.

외부 수집·DB 저장 없이 현재 자료를 분석하고 수집 계획만 생성하려면 다음처럼 실행한다. DB 네트워크 연결은 필요하다.

```powershell
.venv/Scripts/python.exe -m scripts.menu_keyword_pipeline.cli
```

기본 실행은 `outputs`에서 완료 또는 부분 완료된 이 파이프라인의 최신 결과를 자동으로 찾아 비교한다. 직접 지정하려면 `--previous 이전결과폴더`를 추가한다. 저장 경로를 직접 선택하려면 기존처럼 `--output 새결과폴더`를 사용할 수 있으며, 이 경우 같은 상위 폴더에서 이전 결과를 찾는다. 재실행 때 DB의 유효 자료를 재사용한다.

## 선정 기준

1. ERP 운영 매장 중 일관된 Place ID·좌표가 있는 매장을 조회한다. ID 없는 매장은 조사하지 않고 모집단 기록에는 남긴다.
2. POS 코드가 기간 중 한 매장에만 대응하는 경우 매출을 연결한다. 양도 등으로 동일 기간 소유자가 겹치면 보류한다.
3. `inputs/hanchon_menu_keywords.json`의 기존 34개 키워드(기존 9개와 추가 검색량 조사 25개)에 메뉴명을 정확히 매칭한다. 신규 키워드를 LLM으로 생성하지 않는다.
4. 매장별 연결 메뉴 금액·수량을 합산하고 둘 다 양수인 조합을 조사 대상으로 한다. 여러 검색어가 같은 메뉴를 참조할 수 있으므로 키워드별 매출을 합쳐 전체 매출로 사용하지 않는다.
5. 키워드를 중복 제거하고 검색광고 검색량을 조회한다. 기간 정의가 일치하는 7일 이내 관측은 재사용한다. 검색량 구간값·미제공은 수치 0으로 바꾸지 않으며 순위 조사와 최종 추천에서 보류한다. 최소 검색량을 임의로 적용하지 않는다.
6. 정확한 검색량이 있는 판매 확인 매장×키워드에 대해 누락·오래된·실패 순위를 수집한다. 기존 모바일 매장 좌표 광고 제외 상위 20위 수집기를 사용한다.
7. DB를 다시 읽어 유효한 순위에서 미노출인 조합만 후보로 정한다. 매장 안에서 전국 검색량 내림차순, 동률이면 판매수 내림차순으로 정렬한다.

## 실패와 데이터 품질

- 검색량: 청크 최대 5개, 요청 간 최소 15초, 최대 3회 시도와 60/120초 재시도 대기. 인증 오류는 실행을 중단한다. 최종 실패·성공 상태 모두 기존 검색량 DB 저장소에 기록한다.
- 순위: 기존 15초 요청 간격과 60/120초 재시도를 사용한다. 부분 수집·실패를 미노출로 해석하지 않는다. 보안차단 또는 저장 실패 시 기존 중단 정책을 따른다.
- POS: 일별 기록 공백은 휴무·무매출·적재 지연을 구분할 수 없다. 원천의 완전 적재를 보증하지 않는다. 공백·연결 보류가 있으면 `REVIEW_REQUIRED`로 표시하고 전 실행 대비 매출 증감을 계산하지 않는다. 현재 관측한 판매 근거는 보존한다.
- 미연결 메뉴: 서비스·음료·배달료를 포함하여 목록에 없는 모든 기록을 보존한다. 검토 전에 임의 삭제하지 않는다. 다중 메뉴명 매핑은 별도 사유로 남긴다.
- 비교: 연결 목록·설정, ERP 메뉴/POS 매핑, 조사 대상 매장·Place ID·좌표·식별 상태가 달라지면 후보 변화도 비교하지 않는다. 새 자료가 실패한 기존 후보는 제거가 아닌 `HOLD`로 표시한다. 관측이 충분한데 판매 확인 목록에서 사라진 경우도 판매 중단으로 단정하지 않는다.
- 중단 후에는 같은 명령을 다시 실행한다. 새 출력 폴더를 자동 생성하고 미완료 건을 DB 기준으로 다시 판단한다. 프로세스 자체를 감시해 무한 재시작하는 기능은 없다.
