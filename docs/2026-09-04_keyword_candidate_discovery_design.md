# 매장별 네이버 키워드 후보 발굴 모듈 설계

## 1. 문서 목적

본 문서는 외식업 매장별 네이버 플레이스 대표키워드를 추천하기 위한 **키워드 후보 발굴 모듈**의 설계를 정의한다.

기존 검색량 산출기와 순위 수집기는 사용자가 입력한 키워드를 평가할 수 있지만, 키워드 자체를 발견하지는 않는다. 신규 모듈은 자사 리뷰, 자사 메뉴, 브랜드 대표메뉴, 운영팀 제공 키워드 및 네이버 검색광고 연관 키워드를 결합하여 평가 이전 단계의 후보 키워드를 생성한다.

이 문서에서 `후보`는 **LLM에 전달할 리뷰 후보가 아니라, 최종 대표키워드가 되기 전의 키워드 후보**를 의미한다.

## 2. 최종 목표와 범위

### 2.1 최종 목표

매장별로 다음 두 종류의 대표키워드를 발견하고 평가할 수 있는 입력 집합을 만든다.

- 빈집 키워드: 검색수요와 방문 의도는 있으나 상위권 전문 경쟁점 점유가 상대적으로 낮은 키워드
- 경쟁 키워드: 검색수요가 크고 매장 적합성이 높지만 상위권 경쟁도 또한 높은 핵심 키워드

### 2.2 이번 모듈의 책임

- 원문 리뷰에서 검색어로 전환 가능한 표현 추출
- 같은 의미의 표현 정규화
- 매장별 근거와 브랜드 공통 근거 집계
- 검색광고 연관 키워드 및 운영팀 키워드와 결합
- 다음 단계에서 검색량·순위·경쟁도를 평가할 후보 제공

### 2.3 이번 모듈이 하지 않는 일

- 후보의 최종 대표키워드 선정
- 네이버 플레이스 순위 수집
- 검색량 산출
- 빈집·경쟁·제외 최종 분류
- 기존 감성분석 결과를 키워드 적합성의 확정 근거로 사용

위 기능은 기존 또는 후속 평가 모듈의 책임으로 분리한다.

## 3. 전체 데이터 흐름

```text
자사 메뉴 ───────────────┐
브랜드 대표메뉴 ─────────┤
운영팀 제공 키워드 ──────┤
네이버 검색광고 연관어 ──┼─> 후보 통합·정규화 ─> 매장별 키워드 후보
블로그 원문 리뷰 ─────────┤                          │
방문자 원문 리뷰 ─────────┘                          ▼
                                          검색량·순위·적합성 평가
                                                     │
                                                     ▼
                                           빈집 / 경쟁 / 제외
```

후보 생성과 후보 평가를 분리한다. 후보 발굴 단계에서는 넓게 수집하되, 각 후보가 어디에서 생성됐고 어떤 리뷰가 근거인지 추적할 수 있어야 한다.

## 4. 원천 데이터

### 4.1 원문 리뷰

원문 리뷰는 `naverDB`의 다음 테이블에서 읽는다.

| 구분 | 테이블 | 원문 식별자 | 본문 컬럼 | 보조 컬럼 |
|---|---|---|---|---|
| 블로그 리뷰 | `dbo.naver_review_blog` | `review_blog_id` | `context` | `title`, `link` |
| 방문자 리뷰 | `dbo.naver_review_visitor` | `review_visitor_id` | `context` | `keyword` |

두 테이블 모두 `place_id`, `place_name`, `brand`, `brand_type`, `date`를 매장 및 브랜드 범위 판정에 사용한다.

실제 테이블명은 `naver_review_vistore`가 아니라 `naver_review_visitor`이다.

### 4.2 기존 분석 테이블의 사용 범위

`midaworks`의 다음 테이블은 기존 리뷰 감성·의견 분석 결과다.

- `DM_FACT_CLAIM_ANALYZED_NAVER`
- `DM_FACT_CLAIM_ANALYZED_NAVER_YUKSUDANG`

이 테이블의 `labels`, `sentiment_overall`, `naver_keyword`, 기존 의견 카테고리는 키워드 발굴 목적에 맞게 만들어진 값이 아니므로 후보 생성의 확정 근거로 사용하지 않는다. 필요한 경우 원문과의 대조 또는 품질 진단을 위한 참고 자료로만 사용한다.

### 4.3 기타 후보 원천

- 자사 메뉴명
- 브랜드 대표메뉴명
- 운영팀이 제공한 매장별 추천키워드
- 네이버 검색광고 API의 연관 키워드

초기 실행은 파일 입력을 허용한다. 후보 발굴 모듈과 데이터 구조가 안정화된 후 내부 DB 입력 어댑터로 전환한다. 후보 생성 로직은 입력 방식과 분리하여 재사용한다.

## 5. 리뷰 분석 범위와 품질 규칙

### 5.1 기본 기간

기본 분석 창은 실행 기준일 이전 **최근 12개월**이다.

12개월을 사용하는 이유는 다음과 같다.

- 현재 메뉴, 상권 및 소비 표현과 동떨어진 과거 리뷰의 영향을 제한한다.
- 여름 보양식, 겨울 국물요리 등 한 해의 계절성을 포함한다.
- 리뷰가 적은 매장에서도 후보 생성에 필요한 표본을 확보한다.

리뷰의 최신성을 반영하기 위해 후보 근거 점수에는 다음 시간 가중치를 적용한다.

| 리뷰 경과 기간 | 시간 가중치 |
|---|---:|
| 0~3개월 | 1.0 |
| 4~6개월 | 0.8 |
| 7~12개월 | 0.5 |
| 12개월 초과 | 기본 분석 제외 |

12개월 내 유효 리뷰가 부족한 매장은 별도의 보완 규칙을 적용할 수 있다. 최대 24개월 확장은 후속 검증에서 최소 표본 기준과 함께 결정하며, 기본값으로 자동 적용하지 않는다.

### 5.2 유효 리뷰 조건

다음 조건을 모두 충족한 리뷰만 분석한다.

- `date`가 기본 분석 기간 안에 있음
- `date`가 `1900-01-01` 같은 기본값 또는 비정상 날짜가 아님
- `context`가 `NULL`, 빈 문자열 또는 공백 문자열이 아님
- 매장을 연결할 `place_id`가 있음

### 5.3 브랜드 코드 정규화

현재 `brand_type`에는 `01/1`, `02/2`처럼 같은 브랜드를 나타내는 표기가 함께 존재한다. 입력 어댑터에서 앞자리 0을 제거한 정규화 코드로 비교하되, 원본 값도 추적 가능하게 유지한다.

브랜드명 문자열만으로 매장을 판정하지 않고 `place_id`와 정규화된 브랜드 코드를 함께 사용한다.

### 5.4 중복 제거

분석 전에 다음 복합값으로 동일 리뷰를 판정한다.

```text
source_type + place_id + review_date + normalized_context
```

`normalized_context`는 앞뒤 공백 제거, 연속 공백 통합 및 비교 목적의 기본 유니코드 정규화를 적용한 본문이다. 원문 자체는 변경하지 않는다.

최근 12개월 데이터 점검 결과 중복 초과 행은 블로그 31건, 방문자 14건이었다.

### 5.5 확인된 데이터 규모

2026-09-04 확인 기준이다.

| 원천 | 전체 행 | 본문 보유 행 | 최근 12개월 유효 원문 리뷰 수 |
|---|---:|---:|---:|
| 블로그 리뷰 | 44,639 | 9,517 | 2,325 |
| 방문자 리뷰 | 53,129 | 18,801 | 10,138 |
| 합계 | 97,768 | 28,318 | 12,463 |

중복 초과 행 45건을 제외하면 최근 12개월의 분석 대상은 12,418건이다.

## 6. 리뷰 표현 추출과 정규화

### 6.1 추출 대상

원문에서 검색 행동으로 이어질 수 있는 다음 표현을 추출한다.

- 메뉴·음식: `설렁탕`, `순대국`, `수육`, `도가니탕`
- 식사 상황: `혼밥`, `직장인 점심`, `빠른 점심`, `회식`
- 방문 목적: `해장`, `든든한 한 끼`, `보양식`
- 이용 특성: `24시간`, `포장`, `단체식사`
- 맛·재료 특성 중 검색어로 성립 가능한 표현: `진한 국물`, `맑은 국물`, `푸짐한 고기`

단순 감정 표현인 `맛있다`, `좋다`, `친절하다`는 독립 검색어 후보로 바로 채택하지 않는다. 메뉴·상황과 결합되어 실제 검색어로 성립할 때만 후보화한다.

### 6.2 정규화 예시

| 리뷰 표현 | 정규화 후보 | 분류 |
|---|---|---|
| 혼자 먹기 편해요 | 혼밥 | 식사 상황 |
| 점심시간에 빨리 나와요 | 빠른 점심 | 식사 상황 |
| 해장하기 딱 좋아요 | 해장 | 방문 목적 |
| 양이 많고 든든해요 | 든든한 한 끼 | 방문 목적 |
| 국물이 진하고 고기가 많아요 | 진한 국물, 푸짐한 고기 | 음식 특성 |

### 6.3 규칙과 LLM의 역할

규칙·사전·빈도 집계를 우선 사용한다. LLM은 모든 리뷰를 직접 판단하는 기본 엔진이 아니라 다음의 불확실한 표현을 정규화하거나 분류하는 보조 수단이다.

- 사전에 없지만 여러 리뷰에서 반복되는 표현
- 외식 의도와 비외식 의도가 혼합된 표현
- 메뉴명인지 일반 감상인지 규칙으로 구분하기 어려운 표현
- 어느 후보와 같은 의미인지 정규화하기 어려운 표현
- 해당 매장의 검색 키워드로 적합한지 문맥 없이는 판단하기 어려운 표현

LLM 판정은 근거 리뷰와 함께 기록하며, LLM 결과만으로 최종 대표키워드를 확정하지 않는다.

## 7. 후보 생성 기준

### 7.1 후보의 정의

후보 키워드는 원문 또는 다른 후보 원천에서 발견되어 검색량·순위·경쟁도 평가 단계로 전달할 가치가 있는 정규화된 검색 표현이다.

### 7.2 매장별 후보

동일 매장의 서로 다른 유효 리뷰 3건 이상에서 근거가 발견되면 매장별 후보로 승격한다.

시간 가중치를 적용한 언급량은 후보 우선순위에 사용하지만, 서로 다른 리뷰 수 자체도 별도로 보관한다. 같은 리뷰 안에서 동일 표현이 여러 번 등장해도 리뷰 수는 1건으로 계산한다.

### 7.3 브랜드 공통 후보

서로 다른 3개 이상의 자사 매장에서 근거가 발견되면 브랜드 공통 후보로 승격한다. 브랜드 공통 후보는 개별 매장에 자동 추천하지 않고, 해당 매장의 메뉴·리뷰 근거가 있는지 평가 단계에서 다시 확인한다.

### 7.4 기준 미달과 불확실 후보

- 매장 3리뷰 및 브랜드 3매장 기준을 모두 충족하지 못하면 `근거 부족`으로 보류한다.
- 반복되지만 규칙 분류가 불가능하면 `검토 필요`로 분류하고 LLM 보조 분석 대상으로 전달한다.
- 밀키트, 택배, 조리법처럼 매장 방문 목적과 충돌하는 표현은 즉시 삭제하지 않고 `비방문 의도` 근거를 기록한 뒤 평가 단계의 제외 후보로 전달한다.

임계치는 초기값이다. 정답 후보가 있는 검증 표본을 만든 후 정밀도와 재현율을 비교하여 조정한다.

## 8. 신규 테이블 설계

신규 테이블은 `naverDB`에 생성하며 기존 순위 수집 테이블과 분리한다. 정확한 SQL 자료형, 인덱스 및 제약조건은 구현 계획과 DDL 단계에서 확정한다.

### 8.1 `dbo.naver_keyword_discovery_review_term`

리뷰 단위의 추출 근거를 저장한다.

| 논리 컬럼 | 역할 |
|---|---|
| `review_term_id` | 추출 근거 행 식별자 |
| `source_type` | `BLOG` 또는 `VISITOR` |
| `source_review_id` | 원천 리뷰 PK |
| `brand_code` | 정규화한 브랜드 코드 |
| `place_id` | 리뷰 대상 매장 Place ID |
| `review_date` | 리뷰 작성일 |
| `raw_expression` | 원문에서 추출한 표현 |
| `normalized_keyword` | 정규화된 키워드 후보 |
| `term_category` | 메뉴·상황·방문 목적·이용 특성·음식 특성 등 |
| `time_weight` | 리뷰 최신성 가중치 |
| `extraction_method` | 규칙·사전·LLM 등 추출 방식 |
| `review_required` | 사람 또는 LLM 추가 검토 필요 여부 |
| `evidence_excerpt` | 검증 가능한 최소 문맥 |
| `analyzed_at` | 분석 시각 |

원문 전체를 중복 저장하지 않고 원천 테이블의 PK로 연결한다. 검증을 위해 필요한 최소 문맥만 `evidence_excerpt`에 보관한다.

### 8.2 `dbo.naver_keyword_discovery_candidate`

매장별 또는 브랜드 공통 후보의 집계 결과를 저장한다.

| 논리 컬럼 | 역할 |
|---|---|
| `candidate_id` | 후보 식별자 |
| `brand_code` | 정규화한 브랜드 코드 |
| `place_id` | 매장별 후보의 대상 매장; 브랜드 공통 후보는 별도 범위 표시 |
| `candidate_scope` | `STORE` 또는 `BRAND` |
| `normalized_keyword` | 평가할 키워드 후보 |
| `term_category` | 후보 분류 |
| `store_review_count` | 대상 매장의 근거 리뷰 수 |
| `brand_review_count` | 브랜드 전체 근거 리뷰 수 |
| `brand_store_count` | 근거가 발견된 서로 다른 매장 수 |
| `weighted_mention_score` | 시간 가중 언급 점수 |
| `from_menu` | 자사 메뉴 원천 여부 |
| `from_brand_menu` | 브랜드 대표메뉴 원천 여부 |
| `from_operation_keyword` | 운영팀 키워드 원천 여부 |
| `from_searchad_related` | 검색광고 연관어 원천 여부 |
| `from_review` | 리뷰 원천 여부 |
| `candidate_status` | `READY`, `INSUFFICIENT_EVIDENCE`, `REVIEW_REQUIRED`, `EXCLUDED` |
| `generated_at` | 후보 집계 시각 |

후보별 검색량, 순위 및 경쟁도 결과는 이 테이블에 혼합하지 않는다. 후속 평가 결과와 키워드 키 또는 별도 실행 식별자로 연결한다.

## 9. 인터페이스 분리

모듈은 다음 인터페이스로 분리한다.

1. 리뷰 입력 어댑터
   - `naver_review_blog`, `naver_review_visitor`를 공통 리뷰 형식으로 변환한다.
2. 품질 필터
   - 기간, 빈 본문, 비정상 날짜 및 중복을 제거한다.
3. 표현 추출기
   - 규칙과 사전으로 원문 표현을 추출한다.
4. 불확실 표현 판정기
   - LLM 보조 분석이 필요한 표현만 분리한다.
5. 후보 정규화기
   - 유사 표현을 하나의 검색 키워드로 통합한다.
6. 후보 집계기
   - 매장 리뷰 수, 브랜드 리뷰 수, 매장 수 및 시간 가중 점수를 계산한다.
7. 외부 후보 결합기
   - 메뉴, 운영팀 키워드, 검색광고 연관어를 병합한다.
8. 후보 저장소
   - 리뷰 근거와 집계 후보를 신규 테이블에 저장한다.

이 구조를 통해 초기 엑셀 입력을 내부 DB 입력으로 바꾸더라도 추출·정규화·집계 로직은 변경하지 않는다.

## 10. 후속 평가 모듈과의 연결

`READY` 후보는 다음 값을 수집·계산하는 후속 단계로 전달한다.

- 최근 30일 검색량 추정치
- 네이버 플레이스 상위 결과와 자사 매장 순위
- 외식 방문 의도
- 대상 매장 적합성
- 상위권 직접 경쟁점 점유율
- 전문 최적화 매장 비율
- 자사 매장의 현재 노출 가능성

거리 정보는 키워드 발굴의 필수 조건에서 제외한다. 원문 카드의 거리 문구나 별도 대상 좌표 수집에 의존하지 않는다.

## 11. 검증 기준

초기 검증은 육수당과 한촌설렁탕의 일부 매장을 표본으로 수행한다.

- 원천 리뷰 PK로 모든 추출 근거를 역추적할 수 있어야 한다.
- 동일 리뷰가 중복 집계되지 않아야 한다.
- 브랜드 코드 표기 차이 때문에 후보가 분리되지 않아야 한다.
- 같은 리뷰의 반복 표현은 리뷰 수를 증가시키지 않아야 한다.
- 매장별 후보와 브랜드 공통 후보가 구분되어야 한다.
- 운영팀 키워드와 리뷰 후보가 겹치면 하나의 후보로 통합되고 원천 플래그는 모두 유지되어야 한다.
- 비방문 의도 표현이 대표키워드로 바로 채택되지 않아야 한다.
- LLM을 사용하지 않아도 규칙 기반 기본 파이프라인이 실행되어야 한다.
- LLM 판단 결과가 없어도 원문 근거와 불확실 상태가 보존되어야 한다.

후보 품질 검증용 정답 표본을 사람이 작성하고 다음 지표를 비교한다.

- 정밀도: 생성된 후보 중 실제 평가할 가치가 있는 후보의 비율
- 재현율: 사람이 선정한 유효 후보 중 모듈이 발견한 비율
- 정규화 정확도: 같은 의미의 표현이 올바르게 통합된 비율
- 매장 귀속 정확도: 후보가 실제 근거 매장에 올바르게 연결된 비율

## 12. 결정 사항과 미확정 사항

### 12.1 확정 사항

- 원문 리뷰는 `naverDB`에서 직접 조회한다.
- 기존 감성분석 결과를 후보 생성의 확정 근거로 재사용하지 않는다.
- 후보 발굴용 리뷰 근거 테이블과 후보 집계 테이블을 신규 생성한다.
- 기본 분석 기간은 최근 12개월이다.
- 최근 리뷰에 더 높은 시간 가중치를 적용한다.
- 매장별 후보와 브랜드 공통 후보를 구분한다.
- 규칙 기반 분석을 기본으로 하고 LLM은 불확실 표현에만 사용한다.
- 후보 생성과 검색량·순위·경쟁도 평가를 분리한다.
- 초기에는 파일 입력을 허용하고, 후보 발굴 모듈 완성 후 내부 DB 입력으로 전환한다.

### 12.2 구현 전에 검증할 사항

- 매장별 최소 유효 리뷰 수와 24개월 보완 조건
- 메뉴·상황·방문 목적·비방문 의도 사전의 초기 항목
- 한국어 형태소 분석기 도입 여부와 의존성 비용
- LLM 검토 요청 단위, 비용 상한 및 개인정보 제거 규칙
- 검색광고 연관어 확장 깊이와 호출량 제한
- 후보 이력 보존 방식과 실행 단위 식별자
- SQL Server 컬럼 자료형, 고유 제약조건 및 인덱스

## 13. 구현 순서

1. 신규 테이블 DDL 및 검증 SQL 설계

3. 규칙 기반 표현 추출·정규화 구현

5. 메뉴·운영팀 키워드 입력 결합
6. 네이버 검색광고 연관 키워드 결합
7. 불확실 표현 분리 및 선택적 LLM 검토 인터페이스 구현
8. 표본 매장 후보 품질 검증
9. 기존 검색량·순위 수집 파이프라인과 결합
10. 안정화 후 내부 DB 후보 입력 인터페이스 전환
