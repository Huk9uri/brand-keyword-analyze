# 매장별 키워드 발굴 자동화 설계 및 구현 계획

사용자가 승인한 7단계를 하나의 명령으로 연결한다. LLM·메일·예약 실행은 이번 범위에서 제외한다.

## 설계

- `inputs/hanchon_menu_keywords.json`: 기존 9개와 추가 검색량 조사 25개의 메뉴 연결을 정식 설정으로 보관한다. 키워드별 메뉴명은 정확히 일치시킨다. 신규·다중 매핑 메뉴는 검토 목록으로 남긴다.
- `scripts/menu_keyword_pipeline/core.py`: 한국 시간 실행일의 직전 30일, 매장별 매출 집계, 판매 대상 목록, 순위·검색량 판정 및 변화 계산을 담당한다.
- `repository.py`: ERP 모집단과 POS 연결, 기간 내 메뉴·일별 매출을 한 SQL 집계로 조회한다. 검색량·순위는 기존 DB와 수집기를 사용한다.
- `workflow.py`, `cli.py`: 조회→수집→재조회→분석→저장을 연결한다. 기본은 읽기 전용이며 `--collect --allow-write --allow-network`로 실제 수집한다. `--previous`로 이전 결과를 지정한다.
- 산출물: 실행 입력, 상태, 매출 품질, 미연결 메뉴, 조사 목록, 전체 판정, 매장별 후보, 이전 대비 변화, 한국어 보고서. 새 실행 경로에서 DB 정상 자료를 재사용한다.

## 실패·비교 원칙

- 오늘은 제외하며 적재 지연을 이유로 기간을 뒤로 바꾸지 않는다. 일별 기록 공백은 휴무와 구분 불가능하므로 확인 필요로 표시한다.
- 매장 POS 코드 중복·누락과 메뉴 코드의 다중 이름은 임의 배분하지 않는다.
- 검색량 실패/구간값/미제공과 순위 실패는 0 또는 미노출로 바꾸지 않는다. 정확한 검색량과 유효 순위가 있는 후보만 순위를 매긴다.
- 검색량은 최대 3회, 15초 요청 간격과 60/120초 재시도를 적용한다. 순위는 기존 수집기의 15초 간격과 재시도·보안차단 중단 정책을 따른다.
- 수집 후 DB 재조회로 저장 사실을 확인한다. 저장 실패·보안차단은 중단 사유로 남긴다.
- POS가 불완전하거나 비교 조건이 달라지면 매출 증감은 산출하지 않는다. 이전 후보의 자료가 미확인이면 제외가 아닌 보류로 표시한다.

## 구현 순서와 검증

1. 기간 경계, 합산·누락 메뉴, 실패 보류, 변화 판정 테스트를 먼저 실패시킨 뒤 순수 계산 코드를 구현한다.
2. DB 어댑터와 고정 연결 목록을 추가한다. POS 조회 결과의 메뉴 합계와 일별 합계를 대조한다.
3. 외부 수집을 대체한 통합 테스트로 최초 실행·재실행·부분 완료·저장 실패를 확인하고 실행기를 구현한다.
4. CLI 도움말과 관련 회귀 테스트를 실행한다. 실DB에서는 읽기 전용 계획 실행으로 최근 30일 조회 및 산출물 연결을 검증한다. 장시간 전체 수집은 검증 목적으로 자동 시작하지 않는다.

## 구현 후 확인

- 신규 기간·메뉴 집계·보류·비교·재실행·검색량 재시도 테스트와 기존 배치/공유 순위/수집기 회귀 테스트 68개 통과.
- 실제 DB 읽기 전용 실행 경로: `outputs/hanchon-menu-pipeline-20260916-check`.
- 기간: 2026-08-17 이상 ~ 2026-09-16 미만. 기간 내 최신 관측일 2026-09-15, 브랜드 관측 날짜 공백 없음. 개별 매장 공백은 별도 품질 기록.
- 모집단 146개 중 Place ID 없는 10개 제외, ID·좌표 확인 136개 중 POS 코드 없는 4개 보류. 조회 연결 대상 132개.
- 기존 메뉴 연결 34개 키워드에서 판매 확인 조합 3,547건, 현재 관측으로 후보 1,866건, 보류 820건. 정확한 검색량이 있지만 순위 보완이 필요한 조합은 256건.
- 수집 및 DB 쓰기 없이 검증했으므로 부분 완료 상태가 예상 결과다. 신규 수집 실행·예약·LLM·메일 발송은 하지 않았다.
- 독립 코드 리뷰에서 ERP 메뉴 매핑·대상 식별 변경이 판매 없음으로 오인될 수 있는 비교 경로를 발견해 수정했다. 원천 매핑·매장 식별·좌표 해시가 바뀌면 비교를 보류하며 두 경로의 회귀 테스트를 추가했다.
