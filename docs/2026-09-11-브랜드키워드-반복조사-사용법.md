# 브랜드 키워드 반복 조사 — 1차 사용법

## 할 수 있는 일

검토된 후보 설정 하나로 POS 매출·검색량·대표 매장 좌표의 플레이스 순위를 연결한 보고서를 생성한다. 원자료를 보존하고, 같은 입력으로 보고서를 다시 만들 수 있다. 현재 지원 브랜드는 한촌설렁탕이다.

매번 후보 생성·수집·보고서를 별도로 지시할 필요 없이 **“기본 설정으로 브랜드 키워드 반복 조사 실행”**을 요청하면 아래 명령을 실행할 수 있다. 별도의 사용자 스킬을 설치한 상태는 아니며, 실행 코드는 저장소에 있다.

## 기본 실행 — 기존 DB 조회만

작업 폴더: `C:\workspace\brand_analyze`

```powershell
$env:PYTHONIOENCODING='utf-8'
.venv/Scripts/python.exe -m scripts.brand_keyword_research.cli --config inputs/brand_keyword_research.hanchon.json --output outputs/brand-research-new-run
```

기존 자료를 조회하고, 유효기간이 지난 검색량·순위는 오래된 상태로 표시한다. DB를 변경하거나 브라우저를 띄우지 않는다. 기본 매출 기간은 **POS 최신 날짜를 기준으로 한 최신 완료월**이다. 최신 자료가 오래됐으면 경고한다. 매출 기록이 없는 날짜를 매출 0일로 보정하지 않는다.

## 전체 한촌 운영 매장 집계

```powershell
.venv/Scripts/python.exe -m scripts.brand_keyword_research.cli --config inputs/brand_keyword_research.hanchon.json --all-stores --output outputs/hanchon-all-stores-read
```

ERP 운영 매장 전체를 매장 코드별로 조회한다. 매장 뷰에 아직 없거나 Place ID가 없는 매장도 명단에서 제외하지 않는다. 폐점일이 없는 지정 운영 상태의 매장이 모집단이며, 실행 시점의 명단을 입력 파일에 고정한다. SMARTPLACE_ID는 요구하지 않는다.

기존 설정의 7개 후보를 사용하며, 설정에 있는 매장은 기존 관측 식별자와 확인 좌표를 재사용한다. 나머지 매장은 좌표 캐시를 읽는다. 읽기 전용 실행에서 좌표가 없으면 `LOCATION_MISSING`으로 남기고 외부 수집을 시작하지 않는다.

부족한 좌표·검색량·순위를 보강하는 실행:

```powershell
.venv/Scripts/python.exe -m scripts.brand_keyword_research.cli --config inputs/brand_keyword_research.hanchon.json --all-stores --batch-size 100 --collect --allow-write --allow-network --output outputs/hanchon-all-stores-collect
```

좌표는 기존 Place 페이지 확인기로 검증·저장하며, 실패한 매장은 `LOCATION_RESOLUTION_FAILED`로 표시한다. 누락 순위만 최대 100건씩 실행하고 `batch-0001` 등의 폴더에 계획과 결과를 보존한다. 보안 확인·수집 중단·저장 실패가 발생하면 다음 배치를 시작하지 않는다. 원인을 해결한 뒤 새 출력 경로로 같은 명령을 실행하면 DB의 유효 관측을 재사용하여 남은 자료를 조사한다. 파일에 완료 표시만 있다고 건너뛰지 않는다.

### 전체 매장 지표 해석

- TOP10·TOP20 노출률의 분모는 **유효 순위 관측 매장 수**다. 부분 수집·실패·오래된 순위는 분모에서 제외한다.
- 전체 매장 수, 조사 가능 매장 수, 유효 관측 수, 전체 대비 관측 커버리지와 확인된 노출 비율을 함께 표시한다. 예를 들어 146개 중 5개만 유효하면, 유효 5개에서 100% 노출돼도 전체 확인 비율은 3.42%다.
- 미확인에는 ID·좌표 부족 매장도 포함한다. 이를 미노출로 추정하지 않는다. 분모가 0이면 산정 불가다.
- 순위 분포는 1~3위·4~10위·11~20위·유효한 TOP20 미노출·미확인으로 구분한다. 평균·중앙값은 TOP20에 관측된 일반 순위만 계산한다.
- 검색량은 키워드당 전국 PC·모바일·합계 또는 제공 구간을 한 번 표시한다. 매장별 검색량이나 지역별 검색량이 아니며, 매장 수를 곱하지 않는다.

## 부족한 자료까지 수집

```powershell
.venv/Scripts/python.exe -m scripts.brand_keyword_research.cli --config inputs/brand_keyword_research.hanchon.json --output outputs/brand-research-collected-run --collect --allow-write --allow-network
```

유효기간 내 최신 검색량·정상 순위는 재사용한다. 부족한 검색량은 검색광고 도구로, 부족한 순위는 기존 UC·독립 임시 프로필·Selenium 수집기로 조사한다. 최신 시도가 부분 수집·실패면 과거 성공으로 덮지 않는다. 수집기의 중단 조건을 유지하며, 자동 무한 재시도는 하지 않는다.

원문과 적재 영수증을 남기고 DB 재조회 결과로 최종 보고서를 작성한다. POS는 읽기 전용이다. 검색량·순위 수집 모드에서는 기존 naverDB 테이블에 관측값이 추가된다. 후보·평가 결과·실제 플레이스 등록 키워드는 변경하지 않는다.

## 설정 파일

`inputs/brand_keyword_research.hanchon.json`에 현재 검토 후보 7개와 파일럿 매장 5개를 포함했다.

후보마다 아래 내용을 기록한다.

| 항목 | 의미 |
|---|---|
| id | 중복되지 않는 후보 식별자 |
| query | 실제 검색할 표현. 유사어를 자동 합치지 않음 |
| pos_menu_names | 매출에 연결할 ERP 메뉴명 목록. 여러 이름은 합산하므로 중복 없는 검토 필요 |
| evidence | 선정·조사 근거 |
| condition | 판매 여부, 계절성 등 적용 조건 |

예를 들어 삼계탕 검색량에 연결한 POS 금액은 `누룽지반계탕(한촌)` 금액이다. 삼계탕 전체 제품군 매출로 자동 확장하지 않는다. 포장상품이나 새로운 메뉴를 자동 후보로 올리지 않으며, 목록 변경은 검토 후 수행한다.

`ttl_days`는 1~30일, 기본 7일이다. 후보는 최대 20개다. 기존 설정 매장 모드는 후보×매장 최대 100건이며, 전체 매장 모드에는 이 전체 건수 제한이 없고 배치 크기만 1~100건으로 제한한다. 대상 좌표는 근거 URL·확인 시각을 포함하며 장소 변경 시 갱신해야 한다. 현재 뷰의 한촌 공개 Place ID와 일치하는지 조회 시 확인한다. 스마트플레이스 관리 ID는 순위 조사에 필요하지 않다.

## 결과 파일

| 파일 | 내용 |
|---|---|
| report.md | 매출·검색량·TOP10·TOP20·매장별 순위·경쟁점·근거 비교 |
| input.json | DB에서 읽은 동결 원자료와 설정·기준 시각 |
| comparison.json | 후보별 기계 판독용 결과 |
| keyword-summary.csv | 키워드별 검색량·노출률·커버리지·순위 분포 |
| store-ranks.csv | 조사 가능한 매장의 키워드별 순위와 미관측 상태 |
| store-inventory.csv | 전체 모집단과 조사 제외 사유 |
| verification.json | 입력·결과 해시와 불완전 관측 수 |
| status.json | COMPLETE·PARTIAL·FAILED, 실행 단계와 중단 상태 |
| before.json | 수집 모드에서 수집 전 조회 자료 |
| volume-*.json / rank-*.json | 새 수집이 있는 경우 원응답·계획·영수증 |
| inventory-before.json / locations/*.json | 전체 매장 초기 명단과 수집 모드의 좌표 확인 결과 |
| batch-*/plan.json / receipt.json | 전체 매장 모드의 순위 배치별 계획과 처리 결과 |

출력 폴더는 매번 새 경로를 사용한다. 재실행하면 DB의 유효 관측을 재사용하지만 동일 보고서를 덮어쓰지는 않는다. 연결·실행 실패는 비밀정보 없이 단계와 예외 유형을 기록한다.

종료 코드: `0` 비교 자료 확보, `2` 일부 자료 부족·오래됨·수집 중단 등을 포함한 보고서 생성, `1` 실행 실패. `PARTIAL`은 프로그램 오류만을 뜻하지 않는다. 자료가 부족한 후보도 보고서에 남긴다.

## 오프라인 재현

```powershell
.venv/Scripts/python.exe -m scripts.brand_keyword_research.cli --replay outputs/brand-research-new-run/input.json --output outputs/brand-research-replay
```

DB·검색 API 없이 저장된 입력으로 보고서를 생성한다. 최초 수집 시점의 관측과 조건을 재생하는 것이며, 현재 시점의 최신 결과로 갱신하지 않는다.

## 이번 범위에 포함하지 않은 것

- 전체 메뉴에서 후보 자동 발굴 및 추천 점수 계산
- 월별 계절성·메뉴별 판매 가능 일수·마진 보정
- 포장상품·세트 메뉴의 자동 분류와 메뉴군 병합
- 신규 경쟁점 keywordList 수집 및 스마트플레이스 유입 효과 검증
- 웹 화면·자동 스케줄 실행·플레이스 키워드 등록

이 기능은 반복 조사 자동화 1차다. 최신 데이터를 같은 방식으로 모으는 단계이며, 결과 해석과 최종 후보 선택까지 무조건 자동으로 끝내는 기능은 아니다.

## 전체 매장 확장 검증 기록 (2026-09-11)

실제 DB 읽기 전용 실행에서 ERP 운영 매장 146개를 확인했다. Place ID 확인 136개, 좌표 사용 가능 8개, 좌표 부족 128개, Place ID 부족 10개다. 설정 후보 7개의 검색량과 기존 순위 스냅샷 35개를 연결했다. 이는 전체 매장 순위 수집 완료를 뜻하지 않으며 결과 상태는 `PARTIAL`이다. 외부 전체 수집과 DB 쓰기는 이번 구현 검증에서 실행하지 않았다.
