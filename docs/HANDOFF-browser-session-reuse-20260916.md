# HANDOFF — 매장별 순위 수집의 브라우저 재시작 최소화

## 요청과 목표

사용자는 최근 30일 POS 기반 키워드 발굴 파이프라인의 운영 검증에 앞서 수집 효율을 개선하려 한다. 이번 인계 범위는 **매장별 수집 순서를 유지하고, 배치 경계 때문에 같은 매장의 브라우저를 다시 여는 일을 줄이며, 실제 효과를 측정하는 작업**이다.

이 문서는 구현 인계용이다. 문서 작성 시점에는 아래 성능 개선을 구현하거나 실제 수집을 시작하지 않았다.

## 작업 환경과 주의사항

- 저장소: `C:\workspace\brand_analyze`, PowerShell, `.venv/Scripts/python.exe`.
- 설계·구현·운영 문서는 한국어로 작성한다.
- 검색 요청 간격 **15초**, 재시도 대기 **60/120초**를 유지한다. 병렬 브라우저나 요청 빈도 증가는 이번 범위가 아니다.
- 과거 네이버 과도한 접근 차단과 Chrome 임시 프로필 파일 잠금이 있었다. 보안차단 중단, 저장 실패 중단, 프로필 정리·종료 확인 기능을 보존한다.
- 기존 작업의 미커밋 수정이 있다. `git status --short`로 확인하고 덮어쓰거나 되돌리지 않는다. 특히 `browser.py`, `collection.py`, `test_keyword_discovery_uc.py`에는 기존 복구·간격 개선이 포함되어 있다.
- 정기 진행 보고는 사용자 요청으로 중지됐다. 자동화를 다시 켜거나 메일을 보내지 않는다.

## 현재 구현과 호출 경로

1. `scripts/menu_keyword_pipeline/core.py::aggregate`
   - 매장 코드를 정렬한 뒤 해당 매장의 연결 키워드를 순회한다.
   - 따라서 **새 파이프라인은 이미 A매장 전체 키워드 → B매장 전체 키워드 순서**다.
2. `scripts/menu_keyword_pipeline/workflow.py::execute`
   - 판매 확인, 정확한 검색량, 순위 유효성 조건으로 조사 목록을 필터링한다. 기존 순서를 유지한다.
3. `scripts/menu_keyword_pipeline/repository.py::Adapter.collect_rank`
   - `collect_in_batches(..., batch_size=50)`을 호출한다.
4. `scripts/brand_keyword_research/batch_collection.py::collect_in_batches`
   - 유효 자료를 제외한 큐를 고정 50건 단위로 자른다.
   - 각 배치에 `plan.json`, `receipt.json`, 오류 시 `failure.json`을 기록한다.
5. `scripts/keyword_evaluation/collection.py::collect_ranks`
   - 호출마다 새 `BrowserFactory`, `KeywordDiscoveryCollector`, `run_id`를 만든다.
6. `scripts/keyword_discovery_rank/collector.py::KeywordDiscoveryCollector`
   - `run()` 안에서는 같은 세션 프로필의 작업에 브라우저를 재사용한다.
   - `_ensure_session()`에서 기기·좌표 조건이 바뀌면 세션을 교체한다. 구현 시 정확한 프로필 필드를 다시 확인한다.
   - `run()`의 `finally`에서 `_discard_session()`을 호출한다.

**남은 문제:** A매장 작업 중간에 50건 경계가 걸리면 브라우저가 종료되고 다음 배치에서 같은 좌표의 브라우저를 다시 생성한다.

## 기대 효과를 설명할 때 구분할 것

- 과거 키워드별 순서로 1,677건을 수집하던 실행과 새 매장별 순서를 비교하면, 매장 전환·재시작이 크게 줄 수 있다.
- 그러나 이번 추가 개선의 비교 기준은 **이미 매장별로 정렬된 새 파이프라인**이다. 과거 대비 약 1,500회 감소라는 가정을 이번 배치 개선의 효과로 제시하면 안 된다.
- 1,677건을 50건씩 나누면 34배치이며 내부 경계는 33개다. 장애가 없는 경우 고정 배치 경계 제거만으로 줄일 수 있는 동일 매장 재시작은 최대 33회 수준이다. 실제 값은 조사 큐와 경계 위치에 따라 더 작다.
- 실제 최근 30일 읽기 검증에서 순위 보완 대상은 256건이었다. 이 큐라면 고정 50건 배치의 내부 경계는 5개다. 향후 실행에서는 달라진다.
- 요청 수·대기 시간·페이지 로딩은 그대로다. 절감 시간은 실제 재시작 비용을 측정해 산출한다. 속도 개선을 과장하지 않는다.

## 권장 구현 방식

### 우선안: 매장 경계에 맞춰 배치를 나누기

전체 collector 수명 구조를 바꾸기 전에, 새 메뉴 파이프라인에서 **한 매장의 작업 묶음을 가능한 한 나누지 않는 배치 정책**을 적용한다.

- 연속된 같은 매장 작업을 하나의 묶음으로 취급한다. 매장 구분은 명시적 매장/Place ID를 기준으로 하고 좌표만으로 서로 다른 매장을 합치지 않는다.
- 다음 묶음을 넣으면 배치 상한을 넘는 경우, 현재 배치를 먼저 마감하고 새 배치에서 해당 매장을 시작한다.
- 예: A 34건, B 34건, 상한 50 → `[A 34]`, `[B 34]`. `[A 34 + B 16]`, `[B 18]`로 자르지 않는다.
- 여러 매장 묶음 합계가 상한 이하면 같은 배치에 넣을 수 있다. 브라우저는 매장 전환 때 기존 정책대로 교체한다.
- 한 매장의 미완료 작업 수가 상한보다 많으면 기존 상한 안에서 분할한다. 이 예외의 분할 횟수를 기록한다. 현재 연결 목록은 34개지만 향후 확대를 고려한다.
- 기존 공용 수집기의 다른 호출자가 정확한 고정 크기 배치를 기대할 수 있다. 기본 동작은 유지하고, 선택 가능한 배치 정책을 추가해 **메뉴 파이프라인에서만 활성화**하는 방식을 우선 검토한다.
- 이미 매장별인 큐는 불필요하게 재정렬하지 않는다. 일반 입력이 매장별로 묶이지 않은 경우 정책의 계약을 명확히 한다. 기존 다른 호출자의 우선순위를 몰래 바꾸지 않는다.

이 방식은 같은 매장이 배치 사이에 끊기는 것을 줄이면서 기존 `run()`의 종료·정리 책임을 그대로 유지한다. 배치가 달라져도 같은 세션 객체를 공유하는 구조는 우선안에 필수적이지 않다.

### 대안: 여러 배치 사이에서 collector 세션 유지

측정 결과와 요구가 우선안으로 충족되지 않을 때만 검토한다. 이 경우 다음을 모두 설계해야 한다.

- 최상위 소유자가 전체 종료·예외·중단 시 세션을 반드시 정리한다.
- 배치별 run_id, DB 스냅샷, HTML/스크린샷 경로와 영수증을 혼동하지 않는다.
- 배치별 실패 카운터·재시도 상태·요청 대기 규칙의 수명과 초기화를 명확히 한다.
- 보안차단이나 저장 실패 뒤 다음 배치를 실행하지 않는다.
- 단순히 `run()`의 `finally` 정리를 삭제하거나 종료 예외를 숨기지 않는다.

## 측정 항목

실제 시간을 변경하지 않는 별도의 단조 시계로 성능을 측정한다. DB 관측 시각을 기록하는 기존 `clock`과 혼용하지 않는다. 테스트에서는 시계를 주입해 긴 실제 대기를 피한다.

- 전체 작업 수, 실제 시도 수, 재시도 수, 처리·성공·부분·실패·저장 실패 수.
- 브라우저 생성·종료·손상 복구 횟수.
- 같은 매장이 배치 경계에서 분할된 횟수.
- 브라우저 생성 시간, 종료 시간, 검색 호출 시간, 명시적 대기 시간, 전체 경과 시간.
- 경계 분할로 인한 재시작과 좌표 변경·손상 복구로 인한 재시작을 구분한다. 복구에 필요한 재시작을 성능 오류로 취급하지 않는다.
- 배치별 측정과 전체 집계를 영수증 또는 별도 성능 JSON에 저장한다. 기존 필드와 의미를 유지한다.

검색 호출 시간에는 기존 구현상 어떤 단계가 포함되는지 명시한다. 파싱·DB 저장을 측정하지 않았다면 검색 시간에 포함됐다고 설명하지 않는다. 합산 시간이 전체 시간과 다를 수 있으면 차이를 설명한다.

## 구현 순서

1. 기존 코드와 미커밋 변경을 확인하고, 고정 배치·세션 수명·세션 프로필 동작을 다시 읽는다.
2. 실패하는 테스트부터 작성한다. 새 배치 정책이 같은 매장을 상한 내에서 분할하지 않는다는 조건을 검증한다.
3. 매장 경계 배치 정책을 추가하고 메뉴 파이프라인에 연결한다.
4. 세션 생성·종료·검색·대기 측정을 추가한다. 외부 수집 없이 테스트 가능한 시계와 브라우저 대체물을 사용한다.
5. 기존 배치·수집기·프로필 정리·파이프라인 테스트를 실행한다.
6. 저장된 입력으로 구/신 정책의 배치 경계 수와 계획 집합을 비교한다. 이 단계는 네트워크를 사용하지 않는다.
7. 소규모 실수집이 필요한 경우 실제 미완료/만료 대상에서 범위를 정해 한 번 실행한다. 전체 34개 키워드 전량 수집이나 같은 검색어의 반복 벤치마크를 자동 시작하지 않는다. 검증 범위·결과를 사용자에게 명확히 보고한다.
8. 변경 내용, 측정 결과, 남은 운영 검증 범위를 한국어로 기록한다.

## 필수 테스트와 완료 조건

- 2개 이상 매장, 매장당 여러 키워드, 고정 배치 경계가 매장 중간에 걸리는 입력에서 새 정책의 불필요한 분할이 사라진다.
- 모든 미완료 매장×키워드가 정확히 한 번 계획된다. 작업 누락·중복·유효 자료 재수집이 없다.
- 빈 큐에서는 브라우저가 생성되지 않는다.
- 한 매장이 배치 상한을 초과해도 작업이 누락되지 않고 상한 정책이 지켜진다.
- 정상 동작에서 같은 프로필의 여러 검색은 세션 1개를 재사용하며, 좌표/기기 변경 또는 세션 손상 시 필요한 교체는 수행한다.
- 성공·예외·보안차단·저장 실패에서 열린 세션을 정리한다. 보안차단 뒤 추가 검색은 없다.
- 요청마다 15초 대기와 기존 재시도 대기 정책이 보존된다.
- 배치 계획·영수증·DB run_id·증빙 경로가 일관되고 재실행 시 기존 저장 결과를 재사용한다.
- 측정 집계가 테스트의 알려진 횟수·시간과 일치한다. 측정 중 예외가 본래 수집 오류를 가리지 않는다.
- 기존 호출자의 기본 고정 배치 동작이 바뀌지 않는다.

실행 예:

```powershell
.venv/Scripts/python.exe -m pytest tests/test_brand_research_batches.py tests/test_keyword_discovery_collector.py tests/test_keyword_discovery_browser.py tests/test_keyword_discovery_uc.py tests/test_keyword_evaluation_shared_rank.py tests/test_menu_keyword_pipeline.py tests/test_menu_keyword_workflow.py tests/test_menu_keyword_cli.py -q
```

새 테스트를 추가하면 위 목록에도 포함한다. Windows 파일 잠금 등으로 실패하면 성공으로 보고하지 않고 원인과 재검증 결과를 기록한다.
